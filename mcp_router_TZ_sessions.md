# Техническое задание: проброс контекста внешнего пользователя к нижестоящему MCP-серверу

> Версия 2. Переработано с учётом v1/v2-матрицы протокола MCP и выявившихся
> особенностей SDK v2 (mcp==2.3.0). Ключевое отличие от v1: проброс зависит от
> версии протокола **и** внешнего клиента, **и** нижестоящего сервера.

## 1. Введение

### 1.1. Проблема

`mcp_router` выступает одновременно MCP-клиентом (по отношению к нижестоящим
серверам) и MCP-сервером (по отношению к внешним потребителям — Dify, n8n,
Python-агенты). Нижестоящий MCP-сервер может быть **stateful** — например,
Playwright хранит состояние браузера (вкладки, cookies, localStorage, текущую
страницу).

В текущей реализации `mcp_router` держит **один долгоживущий нижестоящий
`Client` на каждый сервер** и использует его для **всех** внешних пользователей.
Следствие: если два внешних клиента (сессии A и B) подключились к `mcp_router`
и оба работают с одним Playwright-сервером, то состояние браузера у них
**общее и не изолированное** — сессия A «видит» действия сессии B и наоборот.

### 1.2. Усложняющий фактор: v1 и v2 протокола MCP

Проброс контекста **не является тривиальной «сквозной» передачей одного поля**.
Механизм и сама возможность проброса зависят от версий протокола на обеих
сторонах:

- **v1 (2025-11-25, session-based).** Клиент и сервер проходят `initialize`
  handshake; сервер назначает `session_id`, клиент присылает его обратно в
  HTTP-заголовке `Mcp-Session-Id`. Контекст/метаданные на каждый запрос не
  передаются (только в момент handshake). `_meta` на запросах `tools/call`
  обычно пуст или отсутствует.
- **v2 (2026-07-28, stateless).** Сессии и `initialize` **полностью удалены**
  (SEP-2567 sessionless + SEP-2575 stateless). Каждый запрос самодостаточен:
  метаданные и идентификаторы клиента передаются в `_meta` **каждого** запроса.
  Состояние между вызовами — явными хэндлами. Заголовок `Mcp-Session-Id`
  остаётся только для обратной совместимости с v1-клиентами.

Ключевое следствие: у роутера **нет** `session_id` от v2-клиента (сессий нет),
поэтому переносить вниз под `session_id_key` нечего. Зато v2-клиент сам кладёт
нужный контекст в `_meta`, и его можно пробросить транзитом.

### 1.3. Цель

Обеспечить нижестоящему MCP-серверу возможность отличать одного внешнего
пользователя от другого и, при желании, изолировать их состояние — **не нарушая
stateless-принцип самого `mcp_router`** и корректно обрабатывая все комбинации
v1/v2 клиента и сервера.

## 2. Матрица v1/v2 (ядро ТЗ)

| # | Внешний клиент | Downstream-сервер | Механизм проброса | Комментарий |
|---|---|---|---|---|
| 1 | v2 | v2 | **Проброс пользовательских ключей `_meta`** (pass-through, транзит) | У роутера нет `session_id`; клиент сам кладёт контекст в `_meta`. Пробрасываем **только пользовательские** ключи (исключая зарезервированные `io.modelcontextprotocol/*`). `session_id_key` **не используется**. |
| 2 | v2 | v1 | **Проброс невозможен** | v1-сервер не имеет механизма `_meta`-проброса для каждого вызова; tools вызываются в рамках одной default-сессии (установленной при handshake) без идентификатора в `_meta`. |
| 3 | v1 | v2 | Проброс `session_id` в поле, заданное `session_id_key` в `config.yaml` | У роутера есть `session_id` v1-клиента (из контекста/`Mcp-Session-Id`). Кладём его в `_meta` под ключом `session_id_key` (см. §5). |
| 4 | v1 | v1 | Проброс `session_id` в поле, заданное `session_id_key` в `config.yaml` | Строго говоря требует отдельной downstream-сессии на каждый входящий `session_id` (вариант B, отклонён, §7) либо проброса `session_id` в `_meta` под `session_id_key`. |

**Решение по реализации:** варианты 1, 3, 4 — проброс через `_meta` (разными
способами). Вариант 2 (v2→v1) — проброс не выполняется, все вызовы идут в
default-сессию нижестоящего сервера. Вариант B (пулы сессий per-пользователь)
отклонён (см. §7).

### 2.1. Как роутер определяет версии

- **Версия внешнего клиента** определяется на входе по форме запроса:
  - v2-клиент шлёт modern-envelope: HTTP-заголовки `mcp-protocol-version` =
    `2026-*` (и `mcp-method`/`mcp-name`), а входящий `_meta` содержит
    зарезервированные ключи `io.modelcontextprotocol/*`.
  - v1-клиент проходит `initialize` handshake и шлёт `Mcp-Session-Id` в
    заголовке; входящий `_meta` на `tools/call` пуст/отсутствует.
- **Версия downstream-сервера** определяется автоматически из результата
  handshake/`Client.protocol_version` (согласованная версия протокола) при
  подключении (`connect`/`list_tools`). v1 → protocol version `2025-*`,
  v2 → `2026-*`.

## 3. Текущая архитектура и её поведение

### 3.1. Как устроен проброс сейчас

```
Внешние клиенты                 mcp_router (stateless)              Нижестоящий сервер
┌──────────┐        /mcp        ┌─────────────────────────────┐
│ Клиент A  │── session_A ─────▶│  ScopedMCPServer             │
└──────────┘                    │  call_tool(name, arguments)  │
┌──────────┐                    │  ↓                           │
│ Клиент B  │── session_B ─────▶│  ClientPool (1 Client/сервер)│──────▶ 1 сессия Playwright
└──────────┘                    │  call_tool(name, arguments)  │        (общая для A и B)
                                └─────────────────────────────┘
```

- Для v1-клиентов внешняя сессия (A или B) различима на стороне роутера
  (через `Mcp-Session-Id`/контекст), но при передаче вниз
  (`_pool.call_tool` → `dc.call_tool`) эта информация **отбрасывается**:
  передаются только `name` и `arguments`.
- Для v2-клиентов сессии нет вообще; входящий `_meta` не пробрасывается.
- Нижестоящий сервер получает все вызовы через **одну** сессию и не может
  отличить клиента A от клиента B.

### 3.2. Ключевые точки кода

| Файл | Функция | Роль |
|---|---|---|
| `src/mcp_router/mcp_server.py` | `ScopedMCPServer.call_tool` | Принимает вызов от внешнего клиента, определяет его версию, извлекает контекст, вызывает `_pool.call_tool` |
| `src/mcp_router/mcp_server.py` | `_extract_session_id` | Извлекает `session_id` v1-клиента из контекста/заголовка `Mcp-Session-Id` |
| `src/mcp_router/mcp_client.py` | `ClientPool.call_tool` | Маршрутизирует по `server.tool` к нужному `DownstreamClient` |
| `src/mcp_router/mcp_client.py` | `DownstreamClient.call_tool` | Вызывает нижестоящий `Client.call_tool`, формирует исходящий `_meta` |
| `src/mcp_router/config.py` | `ServerConfig.session_id_key` | Ключ `_meta` для проброса `session_id` (v1-клиент → сервер) |
| `src/mcp_router/mcp_server.py` / `config.py` | `MCP_PROTOCOL_VERSION` | Глобальный env-ключ: версия протокола, которую роутер принимает как сервер (`auto`/`v1`/`v2`), см. §4.6 |

## 4. Требования

### 4.1. Общие принципы (stateless)

Реализация **не** должна:
- хранить какие-либо данные о внешнем клиенте в памяти между вызовами;
- создавать/закрывать нижестоящие `Client` на основе внешнего клиента;
- вести счётчики, TTL или кэши per-пользователь.

Проброс — чистая «сквозная» передача значения/набора ключей от входящего
запроса к исходящему `_meta`, без промежуточного состояния.

### 4.2. v2-клиент → v2-сервер (pass-through `_meta`)

**Спецификация:**
- Роутер берёт входящий `_meta` запроса (`context.request_context.meta`) и
  пробрасывает его **транзитом** нижестоящему v2-серверу через аргумент `meta`
  (`RequestParamsMeta`) в `Client.call_tool`.
- Пробрасываются **только пользовательские ключи** — все ключи `_meta`,
  **исключая** зарезервированные `io.modelcontextprotocol/*`. Резервные ключи
  SDK нижестоящего сервера заполняет сам; их передача роутером не нужна и
  может конфликтовать.
- `session_id_key` в этом случае **не применяется** (нет `session_id`, значение
  было бы всегда `None`).
- Если пользовательских ключей в входящем `_meta` нет — исходящий `_meta`
  не заполняется (кроме того, что SDK добавит сам).

### 4.3. v1-клиент → v2/v1-сервер (проброс `session_id`)

**Спецификация:**
- Роутер извлекает `session_id` v1-клиента (из `context.request_context.session_id`
  при наличии, иначе из HTTP-заголовка `Mcp-Session-Id`).
- Если `session_id_key` задан в `config.yaml` для сервера и `session_id` получен,
  роутер кладёт `session_id` в исходящий `_meta` под ключом `session_id_key`
  и передаёт его нижестоящему серверу.
- Если `session_id` равен `None` или `session_id_key` не задан (по умолчанию
  `None`/пустой) — поле в `_meta` не формируется, вызов идентичен текущему
  поведению (default-сессия).

### 4.4. v2-клиент → v1-сервер (проброс невозможен)

**Спецификация:**
- Проброс не выполняется. Все вызовы идут в default-сессию нижестоящего
  v1-сервера. `_meta` не заполняется пользовательскими ключами.
- Это задокументированное ограничение матрицы (см. §2, вариант 2), а не ошибка
  реализации.

### 4.5. Правила маршрутизации

- Маппинг «внешний клиент → нижестоящая сессия» остаётся «многие к одному»
  (все внешние клиенты → один долгоживущий `Client` на сервер).
- Контекст/`session_id` используется **исключительно** как метка в исходящем
  `_meta`, а не как ключ выбора нижестоящего `Client`.
- Один и тот же `DownstreamClient` обслуживает все внешние клиенты; различие
  вносится только значением исходящего `_meta`.

### 4.6. Глобальный env-ключ `MCP_PROTOCOL_VERSION` (управление версией роутера)

Версия протокола, с которой `mcp_router` выступает **в роли MCP-сервера** перед
внешними клиентами (т.е. какая версия `MCPServer` обслуживается на `/mcp`),
задаётся глобальным env-ключом:

- Имя переменной: `MCP_PROTOCOL_VERSION`.
- Читается **один раз** при создании `ScopedMCPServer` / конфигурации
  `streamable_http_app` (инициализация соединения) и применяется к настройке
  принимаемой версии протокола.
- По умолчанию (переменная не задана) — `auto`: сервер обслуживает и v1, и v2,
  выбор по первому запросу клиента (поведение SDK v2 по умолчанию).

**Возможные значения** (полный список и их влияние описать в `README.md`):
- `auto` — (по умолчанию) принимать и v1, и v2-клиентов; выбор версии по форме
  запроса.
- `v1` — принудительный downgrade: обслуживать **только** v1-клиентов
  (initialize handshake). v2-клиенты (modern-envelope) отклоняются. Применяется,
  например, когда внешние потребители гарантированно v1 и нужен стабильный
  `session_id` (варианты 3/4 матрицы §2) без конкуренции с modern-путьом.
- `v2` — принудительно **только** v2 (stateless). v1-клиенты (handshake)
  отклоняются.

**Спецификация:**
- Значение передаётся в инициализацию `MCPServer`/`streamable_http_app` на этапе
  создания приложения (см. §8.6).
- Невалидное значение env-переменной → ошибка конфигурации (fail fast) при
  старте.
- Env-ключ — **глобальный** (не per-server), т.к. задаёт версию самого роутера
  как сервера; на нижестоящие серверы не влияет.

## 5. `_meta` и `session_id_key` в `config.yaml`

- `ServerConfig.session_id_key: str | None = None` — ключ в исходящем `_meta`,
  под которым пробрасывается `session_id` **v1-клиента** (варианты 3 и 4
  матрицы).
- По умолчанию `None` → проброс `session_id` выключен (обратная совместимость,
  ничего не меняется). Оператор явно включает его, задав `session_id_key` для
  нужного сервера (например `session_id_key: "mcp_router.session_id"`).
- Если `session_id_key` пуст/`None` — поле в `_meta` не формируется.
- Для v2→v2 `session_id_key` не используется (см. §4.2): проброс идёт целиком
  через пользовательские ключи входящего `_meta`.

## 6. Ограничения и границы ответственности

Проброс **гарантирует только передачу метки/контекста** пользователя. Он **не
гарантирует изоляцию состояния** нижестоящего сервера сам по себе.

**Что делает проброс:**
- нижестоящий сервер получает контекст (`session_id` под `session_id_key`, либо
  пользовательские ключи `_meta`) и тем самым может *различать* внешних
  пользователей;
- если нижестоящий сервер умеет изолировать своё состояние по этому контексту
  (например, Playwright-сервер создаёт отдельный браузерный контекст на
  идентификатор), то параллельные chatflows Dify от разных пользователей будут
  работать изолированно.

**Что проброс НЕ делает:**
- он **не создаёт** отдельных нижестоящих `Client`/сессий/браузеров
  per-пользователь на стороне `mcp_router`;
- если нижестоящий сервер — **один инстанс, разделяемый всеми**, и он **не**
  использует переданный контекст для изоляции, состояние остаётся общим;
- в случае v2→v1 (вариант 2) проброс невозможен в принципе — изоляция
  недостижима силами роутера.

**Следствие для сценария «параллельные chatflows Dify от разных внешних
пользователей»:**
- Гарантированная изоляция достигается **только при условии, что stateful
  нижестоящий сервер реализует изоляцию по полученному контексту**, и что
  клиент и сервер находятся в поддерживаемой комбинации версий (не v2→v1).
- Ответственность за изоляцию лежит на нижестоящем сервере, а не на
  `mcp_router`. `mcp_router` предоставляет лишь механизм различимости
  пользователей.
- Если требуется изоляция **независимо** от нижестоящего сервера (свой
  браузер на каждого пользователя силами самого роутера), это выходит за
  рамки текущего ТЗ и соответствует отклонённому варианту B (§7).

## 7. Отклонённые варианты (для контекста)

### 7.1. Вариант B — пул нижестоящих сессий per-пользователь

`ClientPool` создавал бы отдельный `DownstreamClient` (а значит, отдельный
браузер/состояние) на каждую внешнюю сессию, кешируя их по ключу
`(server, session_id)`.

**Причины отклонения:**
- нарушает stateless-принцип `mcp_router` (появляется runtime-состояние);
- требует политики жизненного цикла: TTL неактивных сессий, закрытие при
  завершении внешней сессии, лимиты числа одновременных сессий, фоновые
  задачи очистки — всё это противоречит «тонкому фасаду»;
- масштабируется плохо: N внешних клиентов × M серверов = N×M нижестоящих
  соединений;
- переносит ответственность за изоляцию на `mcp_router`, тогда как её проще
  и корректнее возложить на сам stateful-сервер.

### 7.2. «session_id_key всегда равен None» для v2→v2

Рассматривался вариант: добавлять поле `session_id_key` в `_meta` даже для
v2→v2, но со значением `None`. Отклонён: это добавляет мусорное поле без
пользы; для v2→v2 корректный проброс — транзит пользовательских ключей `_meta`
(§4.2).

## 8. План реализации

1. **Определение версии downstream (`mcp_client.py`):**
   - после `connect`/`list_tools` фиксировать `Client.protocol_version`
     (`DownstreamClient.protocol_version`); `is_v2 = version.startswith("2026")`,
     иначе v1.
2. **v2→v2 pass-through (`mcp_client.py`):**
   - в `DownstreamClient.call_tool` добавить приём набора пользовательских
     ключей `_meta` (помимо `session_id`);
   - фильтр пользовательских ключей: исключить все ключи с префиксом
     `io.modelcontextprotocol/`;
   - если downstream v2 и есть пользовательские ключи — передать их в
     `client.call_tool(..., meta={...})`.
3. **v1→v2/v1 проброс session_id (`mcp_client.py` + `config.py`):**
   - сохранённая логика: при непустом `session_id` и `session_id_key`
     формировать `meta = {session_id_key: session_id}` (см. §5).
4. **`mcp_server.py`:**
   - в `ScopedMCPServer.call_tool` определить версию внешнего клиента
     (modern-envelope → v2, иначе v1);
   - для v2: извлечь входящий `_meta` (`context.request_context.meta`),
     отфильтровать пользовательские ключи, передать их в `_pool.call_tool`;
   - для v1: извлечь `session_id` (существующая `_extract_session_id`) и
     передать в `_pool.call_tool`.
5. **`run_api.py` (`/run/tool/call`):** REST-вызов не имеет внешней MCP-сессии
   и входящего `_meta`; `session_id = None`, пользовательских ключей нет —
   поведение без изменений.
6. **env-ключ `MCP_PROTOCOL_VERSION` (`mcp_server.py` + `config.py`):**
   - считывать `MCP_PROTOCOL_VERSION` при создании `ScopedMCPServer`/
     `streamable_http_app`; по умолчанию `auto`;
   - `auto` — оставить выбор v1/v2 по первому запросу (поведение SDK по умолчанию);
   - `v1` — принудительно обслуживать только v1: заменить `server/discover`
     handler (не рекламировать modern-версии) и отклонять modern-envelope
     запросы;
   - `v2` — принудительно только v2: отклонять initialize handshake;
   - невалидное значение → `ConfigError` (fail fast) при старте.
7. **Тесты (`tests/`):**
   - v2→v2: при вызове через `/mcp` v2-клиентом пользовательские ключи его
     `_meta` доходят до нижестоящего v2-сервера; зарезервированные ключи
     исключаются;
   - v1→v2 и v1→v1: `session_id` v1-клиента попадает в `_meta` под
     `session_id_key`;
   - v2→v1: проброс не выполняется (в `_meta` нет пользовательских ключей);
   - без `session_id_key` / `session_id` — обратная совместимость;
   - `MCP_PROTOCOL_VERSION`: `auto`/`v1`/`v2` задают ожидаемую принимаемую версию
     (v1-режим принимает v1-клиента и отклоняет v2, и наоборот); невалидное
     значение → ошибка старта;
   - регресс: все существующие тесты продолжают проходить.

---

## 9. Критерии приёмки

- [ ] v2-клиент → v2-сервер: пользовательские ключи входящего `_meta` доходят
      до нижестоящего сервера; зарезервированные `io.modelcontextprotocol/*`
      не пробрасываются.
- [ ] v1-клиент → v2/v1-сервер: при заданном `session_id_key` `session_id`
      v1-клиента попадает в `_meta` под этим ключом.
- [ ] v2-клиент → v1-сервер: проброс не выполняется (нет пользовательских
      ключей в исходящем `_meta`).
- [ ] При `session_id_key = None`/пустом исходящий `_meta` не содержит поля
      `session_id` (обратная совместимость).
- [ ] `/run/tool/call` работает как прежде (без `session_id`/`_meta`).
- [ ] `mcp_router` не создаёт и не хранит ресурсов per-пользователь (нет
      пулов/TTL/кэшей) — stateless сохранён.
- [ ] Версия downstream-сервера определяется автоматически (без ручного
      указания в конфиге).
- [ ] `MCP_PROTOCOL_VERSION`: `auto` — принимает и v1, и v2; `v1` — только v1
      (v2 отклоняется); `v2` — только v2 (v1 отклоняется); невалидное значение →
      ошибка старта.
- [ ] Все существующие тесты проходят; ruff — без замечаний.
